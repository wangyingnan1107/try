# 项目技术分析报告

版本日期：2026-03-25  
适用对象：不懂技术的管理层、业务负责人、项目决策人

## 一、先说结论

这个项目本质上不是一个“普通网页工具”，而是一套“本地采集 + AI结构化分析 + 可视化展示”的轻量知识加工系统。  
它把小红书页面上的原始内容抓下来，存入本地数据库，再调用大模型把内容整理成“摘要、方法、任务、证据、行动建议”等固定结构，最后由网页直接把这些结构化结果展示出来。

领导最关心的几个问题，可以直接概括为：

1. 它为什么能做到“所见即所得”  
   因为页面展示的内容，直接来自数据库里保存的原始 JSON 和分析 JSON，不需要人工二次搬运或手工排版。

2. 数据存在哪里  
   主数据存储在项目根目录的 `rednote.db` 本地数据库文件中；如果下载图片，则图片保存在 `downloads/` 目录中。

3. 它是不是完全本地运行  
   不是。它是“本地优先”，但分析能力依赖外部大模型接口。也就是说，数据先落本地，再把需要分析的内容发给配置好的 AI 接口处理。

4. 它的核心价值是什么  
   不是“保存一篇帖子”，而是把零散内容变成可以复用、可检索、可复盘、可二次组合的知识资产。

## 二、项目在业务上的作用

如果用管理层能理解的话来描述，这个系统相当于一个“内容采集与知识整理中台”的雏形。

它解决的不是“看帖子”，而是下面几个问题：

1. 把分散在平台页面里的内容，稳定抓取下来，避免信息看过就丢。
2. 把帖子从“原始素材”变成“结构化知识”，降低团队二次整理成本。
3. 把单篇内容升级成“学习卡片”，把多篇内容升级成“专题报告”。
4. 把采集、分析、展示、存档串成一个闭环，让内容沉淀到公司自己可控的本地数据里。

换句话说，这个项目不是在做“浏览器收藏夹”，而是在做“内容资产化”。

## 三、系统是怎么跑起来的

整个系统可以分成 4 层：

### 1. 浏览器采集层

项目通过一个油猴脚本挂在小红书页面上。  
用户打开小红书笔记后，页面右下角会出现“采集灵感”按钮。点击后，脚本会直接从当前页面读取：

- 标题
- 正文
- 作者
- 图片地址
- 点赞/收藏/评论数
- 前几条评论
- 当前页面链接

然后脚本把这些内容打包成一份标准 JSON，发送给本地服务。

这一步可以理解为：把“肉眼看到的页面内容”转成“机器可保存的结构化对象”。

### 2. 本地服务层

本地服务使用 FastAPI 提供接口，负责接住浏览器发来的数据，并完成三类动作：

1. 存原始数据
2. 调用 AI 做分析
3. 把分析结果再写回数据库，并提供给前端页面读取

它同时还负责：

- 批量分析
- 多篇整合分析
- 删除帖子
- 删除报告
- 下载图片到本地
- 跟踪整合任务进度

### 3. AI 分析层

系统会把帖子内容组织成统一的输入格式，再调用配置好的大模型接口。  
模型返回的不是一段散文，而是固定 JSON 结构，比如：

- 一句话总结
- 关键词
- 核心收获
- 方法步骤
- 原文证据片段
- 常见误区
- 练习任务
- 24小时行动建议

如果是多篇帖子一起分析，还会额外产出：

- 跨帖共识
- 跨帖分歧
- 知识关系图

所以它不是“让 AI 随便写一段结论”，而是“要求 AI 按公司定义好的格式出结果”。

### 4. 页面展示层

前端页面是一个本地网页控制台，左侧展示帖子和报告列表，右侧展示详情。  
它会直接读取后端返回的 JSON，并按固定区域渲染：

- 原始笔记内容
- AI 学习提炼
- 单篇分析结果
- 跨帖整合报告
- 任务进度状态

因此，页面并不是单独再维护一套展示数据，而是直接消费数据库中的结构化结果。

## 四、这个项目为什么能做到“所见即所得”

这里的“所见即所得”，不是传统文字编辑器意义上的富文本，而是指：

“用户在页面上看到的内容，和系统实际存储、分析、返回的数据，是同一份结构化结果，没有中间人工转抄环节。”

它能做到这一点，靠的是下面 4 个设计。

### 1. 采集结构、存储结构、展示结构是同一条链

浏览器采集到的数据，会被打包为 `RawPost` 结构；  
后端把这份完整 JSON 原样保存到数据库的 `posts.raw_json` 字段；  
前端读取帖子列表时，又会把这个 JSON 重新解析出来展示。

这意味着：

- 页面看到的原始帖子内容，来自原始采集数据
- 页面看到的 AI 分析内容，来自 AI 输出后的结构化 JSON
- 中间没有人为复制粘贴和再次录入

### 2. AI 输出被强制约束为固定 JSON

系统在调用大模型时，不是让模型“自由发挥”，而是明确要求模型只返回 JSON。  
这样做的管理价值很大：

- 前端可以稳定显示
- 数据库可以稳定保存
- 后续可以稳定搜索、统计、复用
- 同一类内容能保持统一格式

如果 AI 返回格式不标准，后端还会先做清洗，再尝试解析，尽量转成标准结构。

### 3. 前端直接渲染完整分析结果

单篇分析结果会完整保存到 `insights.full_json`。  
当前端读取帖子列表时，会把每篇帖子最新版本的分析结果取出来，直接作为 `post.insight` 使用。  
也就是说，前端展示的不是拼接好的静态文案，而是数据库里的标准结果对象。

多篇整合报告同理，完整保存到 `reports.content_json`，前端再直接解析和展示。

### 4. 最新版本自动生效

这个系统支持“重新分析”。  
同一篇帖子每次重新分析后，都会生成一个新版本，并把旧版本标记为非最新。  
前端查询时默认只拿最新版本，所以领导看到的页面结果，永远是“当前有效版本”。

这也是“所见即所得”能长期成立的原因，因为它不是一次性写死，而是有版本管理机制。

## 五、从一篇帖子到最终展示，完整流程是什么

下面用最直白的方式说明一次完整闭环。

### 第一步：用户在小红书页面点击“采集灵感”

浏览器脚本从当前页面抓取内容，生成一份原始数据对象。

### 第二步：本地服务接收并入库

后端接收后，会把原始帖子写入 `posts` 表。  
此时这篇帖子已经在本地落库，即使后面分析失败，原始数据也不会丢。

### 第三步：触发 AI 分析

用户可以对单篇内容分析，也可以批量分析。  
后端会读取帖子内容，拼接正文、评论、互动数据等信息，必要时还会尝试读取图片内容。

### 第四步：大模型返回结构化结论

AI 返回统一格式的 JSON。  
后端会做格式清洗、字段补齐、异常兼容，然后写入 `insights` 表。

### 第五步：页面刷新后直接显示结果

前端再请求 `/api/posts` 时，后端会把帖子和它最新的一份分析结果一起返回。  
页面就能立即显示：

- 原始帖子
- 一句话结论
- 学习收获
- 方法步骤
- 练习任务
- 风险提示
- 下一步动作

这就是一条标准的“采集 -> 分析 -> 展示 -> 存档”闭环。

## 六、多篇内容整合报告是怎么做出来的

除了单篇分析，这个系统还支持多篇整合，也就是把若干篇帖子合并为一个专题学习报告。

它的做法不是简单拼接，而是：

1. 先把多篇帖子做结构化抽取
2. 给不同信息片段打权重
3. 合并成一份“有重点的上下文”
4. 交给 AI 生成跨帖学习报告
5. 把结果保存到 `reports` 表

整合报告会包含：

- 跨帖总结
- 学习路径
- 共识点
- 分歧点
- 概念关系
- 原文证据片段

对管理层来说，这部分价值非常直接：它把“很多零散信息”变成“一份可汇报、可复盘的总结”。

## 七、数据到底存在哪里

这是最重要的问题之一。

### 1. 主数据库

主数据库文件位置：

`项目根目录/rednote.db`

这是当前代码里真正使用的数据库文件。  
项目中还存在一个 `rednote_data.db`，但目前是空文件，不是系统实际主库。

### 2. 原始帖子存储

原始采集内容保存在 `posts` 表，核心字段包括：

- `id`：帖子唯一标识
- `title`：标题
- `content`：正文
- `author_name`：作者
- `raw_json`：完整原始 JSON
- `status`：分析状态
- `error_msg`：失败原因
- `created_at`：入库时间

其中最关键的是 `raw_json`。  
这代表系统不是只存几个摘要字段，而是把完整采集对象保存在本地，后续可以随时还原。

### 3. 单篇分析结果存储

单篇 AI 分析结果保存在 `insights` 表，核心字段包括：

- `post_id`：关联哪篇帖子
- `summary_text`：一句话摘要
- `analysis_json`：分析字段
- `expansion_json`：扩展字段
- `full_json`：完整分析结果
- `version`：第几版分析
- `is_latest`：是不是当前生效版本
- `created_at`：分析时间

其中最关键的是 `full_json`。  
前端页面就是依赖这份完整 JSON 来直接展示分析内容。

### 4. 多篇整合报告存储

整合报告保存在 `reports` 表，核心字段包括：

- `title`：报告标题
- `content_json`：完整整合报告 JSON
- `source_post_ids`：来源帖子 ID 列表
- `created_at`：生成时间

### 5. 任务进度存储

整合分析的执行进度保存在 `aggregation_jobs` 表，用来告诉前端：

- 是否排队中
- 是否处理中
- 当前进度百分比
- 当前阶段说明
- 是否失败
- 对应报告 ID

### 6. 图片文件存储

如果用户触发“下载图片”功能，图片会保存在：

`项目根目录/downloads/`

系统会按帖子标题创建文件夹，再把每张图片写进去。  
这部分是文件存储，不是在数据库里。

### 7. OCR 临时文件

如果启用 OCR，图片会先下载到临时文件，识别后删除。  
也就是说，OCR 的中间文件不是长期保存资产，长期保存的是识别后的文字结果。

## 八、当前项目的真实运行状态

截至 2026-03-25，在当前本地环境下可以确认：

- 主库为 `rednote.db`

这说明该项目不是纯原型文档，而是已经具备实际可运行、可验证的闭环能力。

## 九、这套架构的优点

### 1. 本地优先，资产可控

采集结果和分析结果先进入本地数据库，核心资产掌握在自己手里，不依赖第三方平台后台做存档。

### 2. 结构统一，便于复用

不管是单篇分析还是整合报告，都统一成 JSON 结构，后面可以继续接搜索、报表、知识库、训练集等能力。

### 3. 页面与数据强绑定，维护成本低

由于展示依赖标准结构，前端不用维护大量手工模板，后续新增字段也比较容易扩展。

### 4. 支持版本化

重新分析不会覆盖旧结果，而是生成新版本，这对于追踪模型效果、比对不同分析结果非常有价值。

### 5. 能从“素材”升级为“报告”

这意味着系统不只适合个人收藏，也适合团队共用、专题研究、周报汇总、培训沉淀。

## 十、这套架构的边界和风险

领导层通常更关心“不足和风险”，这一部分建议明确。

### 1. 不是完全离线系统

虽然数据先存本地，但 AI 分析依赖外部接口。  
因此只要进行了分析，请求内容就会发送到配置的模型服务商。

这意味着项目在数据安全上属于：

“本地存储为主，外部模型协同处理”

而不是“全流程不出网”。

### 2. OCR能力已经预留，但当前默认主路径不是 OCR 优先

代码中已经集成了 OCR 服务，也设计了“先 OCR、再分析”的完整管线。  
但从当前实际调用链看，帖子采集后默认并不会自动走完整 OCR 流程，而是分析时优先依赖正文内容，并在有图片时尝试直接做视觉分析。

这意味着：

- OCR 是已具备能力
- 但当前默认主流程更偏向“文本 + 图片直传模型”
- 如果未来要强调图片文字识别的稳定性，建议把 OCR 正式接入默认流水线

### 3. 页面采集依赖目标网站 DOM 结构

浏览器脚本靠页面元素选择器抓数据。  
只要小红书页面结构发生明显变化，采集脚本就可能需要调整。

这是所有页面抓取型工具的共性风险。

### 4. 静态展示虽然稳定，但样式与结构耦合

当前前端展示依赖固定 JSON 字段。  
这带来稳定性，同时也意味着如果未来大改数据结构，前后端要同步调整。

### 5. 数据库目前是单机 SQLite

SQLite 很适合单机工具、小团队、原型期和轻量生产环境。  
但如果未来要多人协同、并发访问、权限管理、集中部署，就需要考虑升级到服务型数据库。

## 十二、管理层最值得关注的三件事

### 1. 它已经具备基础闭环

不是单点功能，而是从采集到报告的完整链路已经跑通。

### 2. 数据资产已经开始落地到本地

帖子、分析结果、报告都已经能以结构化方式保存在自己的数据库里。

### 3. 后续扩展空间很大

在现有基础上，后续可以继续扩展为：

- 企业知识库入口
- 内容选题分析台
- 培训学习辅助平台
- 行业情报沉淀工具
- AI 辅助研究台

## 十三、建议的后续动作

如果从项目推进角度给建议，优先级可以按下面排：

1. 明确是否要把 OCR 接入默认流水线，提升图片型笔记的稳定提取能力。
2. 为数据库增加备份策略，避免本地单机文件损坏带来资产损失。
3. 对外部 AI 接口制定数据安全边界，明确哪些内容允许发送、哪些内容必须脱敏。
4. 补充“采集成功率、分析成功率、报告生成耗时”等运营指标，方便管理层看产出效率。
5. 如果未来多人共用，再评估从 SQLite 升级到服务端数据库。
